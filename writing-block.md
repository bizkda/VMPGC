# 1. Introduction

VMPGC is a compiler and virtual machine project that implements a small, statically typed programming language called Toy.

The project demonstrates how source code written by a programmer is transformed into bytecode, loaded by a virtual machine, and eventually executed by the physical CPU.

It also implements a precise Garbage Collector (GC) responsible for automatically managing dynamically allocated memory.

The main components are:

- A Python compiler.
- A custom bytecode format (`.tbc`).
- A virtual machine implemented in C.
- Two Garbage Collection algorithms.
- A heap verifier.
- A web-based visualizer.

# 2. The complete execution pipeline

When a programmer writes:

```java
2 + 3 * 4
```

The expression passes through several stages before being executed.

For the Toy language, we place it inside a valid function:

```java
fun main(): int {
    print(2 + 3 * 4);
    return 0;
}
```

The complete pipeline is:

```text
       SOURCE CODE
         prog.toy
             |
             v
    +------------------+
    | Python Compiler  |
    +------------------+
             |
             v
          Lexer
             |
          Tokens
             |
             v
          Parser
             |
            AST
             |
             v
       Type Checker
             |
         Typed AST
             |
             v
        Code Generator
             |
          Bytecode
             |
             v
       Binary Writer
             |
          prog.tbc
             |
             v
    +------------------+
    |     C VM         |
    +------------------+
             |
           Loader
             |
         Interpreter
             |
       Heap / Garbage
          Collector
             |
             v
       Native Machine
          Instructions
             |
             v
            CPU
             |
             v
           OUTPUT
             14
```

Each stage has a specific responsibility.

# 3. The Python compiler

The compiler transforms human-readable source code into bytecode that the virtual machine understands.

It consists of four major stages.

## 3.1 Lexer — Lexical analysis

The lexer reads the source code character by character and groups characters into tokens.

For example:

```java
2 + 3 * 4
```

Produces:

```text
INTEGER(2)
PLUS(+)
INTEGER(3)
MULTIPLY(*)
INTEGER(4)
```

The lexer does not understand the mathematical meaning of the expression. It only identifies the different tokens.

## 3.2 Parser — Syntax analysis

The parser receives the tokens and constructs an Abstract Syntax Tree (AST).

For our expression:

```java
2 + 3 * 4
```

The AST is:

```text
       Binary(+)
       /       \
      2       Binary(*)
              /       \
             3         4
```

The tree represents operator precedence.

Multiplication has higher precedence than addition, so the parser places the multiplication operation deeper in the tree.

The parser therefore determines the correct structure of the expression.

## 3.3 Type Checker — Semantic analysis

The type checker verifies that the program respects the language's typing rules.

For example:

```java
2 + 3 * 4
```

The checker verifies:

- `2` has type `int`.
- `3` has type `int`.
- `4` has type `int`.
- `3 * 4` produces an `int`.
- `2 + (3 * 4)` produces an `int`.
- `print` accepts the resulting value.

If an expression contains incompatible types, the checker reports a semantic error before code generation.

## 3.4 Code Generator — Bytecode generation

The code generator traverses the AST and generates bytecode instructions.

For arithmetic expressions, it uses a post-order traversal:

1. Generate the left operand.
2. Generate the right operand.
3. Generate the operator.

For:

```java
2 + 3 * 4
```

The generated bytecode is:

```text
0   PUSH_INT 2
1   PUSH_INT 3
2   PUSH_INT 4
3   MUL
4   ADD
5   PRINT_INT
6   PUSH_INT 0
7   RET
```

The order ensures that multiplication happens before addition.

# 4. Understanding bytecode

Bytecode is an intermediate representation between the source language and machine code.

Instead of directly generating CPU instructions, the compiler generates instructions understood by our virtual machine.

Each instruction contains:

- An opcode.
- An operand, when required.

For example:

```text
PUSH_INT 25
```

Contains:

```text
Opcode:   PUSH_INT
Operand:  25
```

## 4.1 What is an opcode?

An opcode (operation code) identifies the operation that the virtual machine must execute.

Our VM uses numeric opcodes instead of textual instruction names.

For example:

```text
01 = PUSH_INT
06 = ADD
08 = MUL
1d = PRINT_INT
16 = RET
```

The opcode is necessary because the VM needs to distinguish between different operations.

Without it, the VM would not know whether a value represents an arithmetic operation, a jump, a function call or an allocation.

Numeric opcodes also provide:

- Compact bytecode.
- Efficient instruction decoding.
- A fixed instruction format.

## 4.2 Instruction format

In VMPGC, each instruction occupies 8 bytes:

```text
4 bytes: OPCODE
4 bytes: OPERAND
```

For example:

```text
PUSH_INT 2
```

Can be represented as:

```text
01 00 00 00 02 00 00 00
```

The first four bytes represent the opcode.

The next four bytes represent the operand.

Both values are encoded as 32-bit integers.

The textual instruction name is not stored in the binary file.

## 4.3 Understanding all opcodes

### Stack manipulation

| Opcode | Operand | Operation |
|---|---|---|
| PUSH_INT | Integer value | Pushes an integer |
| PUSH_NULL | None | Pushes a null reference |
| POP | None | Removes the top stack value |
| LOAD_LOCAL | Local slot index | Pushes a local variable |
| STORE_LOCAL | Local slot index | Stores the top value in a local variable |

### Arithmetic operations

| Opcode | Operand | Operation |
|---|---|---|
| ADD | None | Pops two values and pushes their sum |
| SUB | None | Pops two values and pushes their difference |
| MUL | None | Pops two values and pushes their product |
| DIV | None | Pops two values and pushes their quotient |
| MOD | None | Pops two values and pushes their remainder |
| NEG | None | Negates the top integer |
| NOT | None | Performs logical negation |

### Comparison operations

| Opcode | Operand | Operation |
|---|---|---|
| EQ | None | Checks equality |
| NE | None | Checks inequality |
| LT | None | Checks less than |
| LE | None | Checks less than or equal |
| GT | None | Checks greater than |
| GE | None | Checks greater than or equal |

Comparison instructions pop two values and push an integer representing a Boolean result:

```text
1 = true
0 = false
```

### Control flow

| Opcode | Operand | Operation |
|---|---|---|
| JMP | Target instruction index | Unconditional jump |
| JZ | Target instruction index | Pops a value and jumps if it is zero |
| CALL | Function index | Calls a function |
| RET | None | Returns from a function |

JMP and JZ are used to implement conditional statements and loops.

### Memory and object operations

| Opcode | Operand | Operation |
|---|---|---|
| NEW | Type ID | Allocates a struct |
| NEW_ARRAY | Type ID | Allocates an array using its size from the stack |
| GETFIELD | Field index | Reads a field from an object |
| PUTFIELD | Field index | Writes a field in an object |
| ALOAD | None | Reads an array element |
| ASTORE | None | Writes an array element |

### Output operations

| Opcode | Operand | Operation |
|---|---|---|
| PRINT_INT | None | Prints an integer |
| PRINT_BOOL | None | Prints a Boolean |

# 5. Understanding the operand stack

The virtual machine uses an operand stack to execute instructions.

The stack follows the LIFO principle:

**Last In, First Out.**

For example:

```text
PUSH_INT 2
PUSH_INT 3
PUSH_INT 4
MUL
ADD
```

The execution is:

```text
Step 1: PUSH_INT 2

       [2]


Step 2: PUSH_INT 3

       [2, 3]


Step 3: PUSH_INT 4

       [2, 3, 4]


Step 4: MUL

       Pop 4
       Pop 3
       Calculate 3 * 4 = 12
       Push 12

       [2, 12]


Step 5: ADD

       Pop 12
       Pop 2
       Calculate 2 + 12 = 14
       Push 14

       [14]
```

Then:

```text
PRINT_INT
```

Pops the value and prints:

```text
14
```

The stack is fundamental to the execution of the virtual machine.

# 6. The C Virtual Machine

Once the compiler generates the `.tbc` file, the C virtual machine takes over.

The VM has several responsibilities.

## 6.1 Loader

The loader reads the compiled binary file.

It checks:

- The file magic (`TBC1`).
- The file structure.
- The instructions.
- The function table.
- The type descriptors.
- The stack maps.

After successful loading, the VM has the information required to execute the program.

## 6.2 Interpreter

The interpreter executes the bytecode.

It maintains a Program Counter (PC), which represents the index of the instruction currently being executed.

The interpreter follows this general loop:

```c
while (running) {

    instruction = instructions[pc];

    opcode = instruction.opcode;
    operand = instruction.operand;

    switch (opcode) {

        case PUSH_INT:
            push(operand);
            break;

        case ADD:
            b = pop();
            a = pop();
            push(a + b);
            break;

        case MUL:
            b = pop();
            a = pop();
            push(a * b);
            break;

        // Other instructions...
    }

    pc++;
}
```

This is a simplified illustration of the interpreter.

The actual VM handles instruction-specific control flow, function calls, returns and runtime errors.

## 6.3 How does the CPU execute the program?

An important distinction:

The physical CPU does not directly understand Toy or VMPGC bytecode.

The C virtual machine is first compiled by a native compiler such as GCC.

For example:

```text
interp.c
    |
    v
   GCC
    |
    v
Native executable: gcvm
    |
    v
Physical CPU
```

When we execute:

```bash
./vm/gcvm program.tbc
```

The CPU executes the native machine instructions of `gcvm`.

Those native instructions implement the bytecode interpreter.

For example, the C instruction:

```c
push(a + b);
```

is compiled into machine instructions that perform an addition and manipulate the VM's stack memory.

Therefore:

**The CPU executes the virtual machine, and the virtual machine interprets our bytecode.**

# 7. Garbage Collection

Garbage Collection is the automatic management of dynamically allocated memory.

When a program creates objects, they are stored in the heap.

Over time, some objects become unreachable because the program no longer has a way to access them.

The GC identifies these objects and reclaims their memory.

## 7.1 Stack and Heap

Two important memory areas are involved.

### Stack

The stack stores function execution information, local variables, parameters and operand values.

Example:

```java
int age = 20;
Person p = new Person();
```

Simplified representation:

```text
STACK
+----------------+
| age = 20       |
+----------------+
| p = reference  | --------+
+----------------+         |
                           |
                           v
HEAP                 +-----------+
                     | Person    |
                     | Object    |
                     +-----------+
```

### Heap

The heap contains dynamically allocated objects.

For example:

```java
Person p = new Person();
```

The object is allocated in the heap, while the variable `p` holds a reference to it.

The GC primarily manages the heap but needs information from the stack and other roots to identify reachable objects.

## 7.2 Reachability

Reachability is the fundamental concept behind tracing Garbage Collection.

An object is reachable if it can be accessed by following references starting from GC roots.

Typical roots include:

- Local variables in active functions.
- Function parameters.
- Global or static references.
- References maintained by the runtime.

Example:

```java
Person a = new Person();
Person b = new Person();

a.friend = b;
b = null;
```

Even though `b` is null, the second object is still reachable through:

```text
Stack       Heap

a --------> Person A
                |
                | friend
                v
            Person B
```

If we then execute:

```java
a = null;
```

Both objects become unreachable and can be collected.

## 7.3 Mark and Sweep

Mark and Sweep is a tracing Garbage Collection algorithm.

It consists of two phases.

**Phase 1: Mark**

The GC starts from the roots and follows all references.

Every reachable object is marked.

**Phase 2: Sweep**

The GC scans the heap and reclaims objects that were not marked.

Example:

```text
Before GC:

[A] [B] [C] [D] [E]

Roots:
  |
  v
  A ---> B ---> C

Mark phase:

[A✓] [B✓] [C✓] [D ] [E ]

Sweep phase:

[A✓] [B✓] [C✓] [FREE] [FREE]
```

The reachable objects survive, while unreachable objects are reclaimed.

## 7.4 Reference Counting

Reference Counting is another GC technique.

Each object maintains a counter representing the number of references pointing to it.

For example:

```java
Person a = new Person();
Person b = a;
Person c = a;
```

The object has three references.

When references are removed, the counter decreases.

When the counter reaches zero, the object can be freed.

However, basic reference counting has a problem with circular references.

For example:

```text
Object A ------> Object B
   ^                 |
   |                 |
   +-----------------+
```

Even if neither object is reachable from the program's roots, both counters remain nonzero.

This is why tracing collectors such as Mark and Sweep are useful.

## 7.5 Stop-and-Copy (Cheney)

VMPGC also implements a copying collector using Cheney's algorithm.

The heap is divided into two regions:

- From-space: Contains currently allocated objects.
- To-space: Receives reachable objects during collection.

The process:

1. Find reachable objects.
2. Copy surviving objects into To-space.
3. Update references to the copied objects.
4. Discard the old From-space.
5. Swap the roles of the two regions.

Conceptually:

```text
BEFORE:

FROM-SPACE             TO-SPACE

[A] [B] [C] [D]        [EMPTY]

AFTER:

FROM-SPACE             TO-SPACE

[OLD SPACE]            [A] [B] [C]
```

Only reachable objects are copied.

This also helps reduce memory fragmentation because surviving objects are placed together.

## 7.6 Generational Garbage Collection

Another important GC concept is Generational Collection.

It is based on the observation that many objects die shortly after being created.

The heap can be divided into:

- Young Generation: Newly allocated objects.
- Old Generation: Objects that survive multiple collections.

Young objects are collected frequently, while older objects are collected less frequently.

This technique is common in production garbage collectors, although it is not one of the two collectors currently described for VMPGC.

# 8. Precise Garbage Collection in VMPGC

This is one of the most important aspects of the project.

A precise GC never guesses whether a value is a pointer.

It knows exactly which locations contain references and which contain primitive values.

VMPGC achieves this through two important structures:

1. StackMap.
2. TypeEntry.

## 8.1 StackMap

A StackMap describes which local variables and operand-stack slots contain references at a safepoint.

Its structure:

```python
@dataclass
class StackMap:
    pc: int
    depth: int
    locals_mask: int
    stack_mask: int
```

Each attribute has a purpose.

| Attribute | Meaning |
|---|---|
| pc | Instruction index associated with the safepoint |
| depth | Number of operand-stack values after operands are popped, at the defined safepoint point |
| locals_mask | Identifies reference-containing local variables |
| stack_mask | Identifies reference-containing operand-stack slots |

A bit of 1 means reference.

A bit of 0 means a non-reference value.

Example:

```text
Operand stack:

+-------------+
| Object A    |  Bit 2 = 1
+-------------+
| Integer 42  |  Bit 1 = 0
+-------------+
| Object B    |  Bit 0 = 1
+-------------+

stack_mask = 101 binary
           = 5 decimal
```

Similarly, `locals_mask` describes the reference locations in the function's local variables.

The compiler generates these maps at the relevant allocation and function-call safepoints.

In the described implementation, these include:

- NEW
- NEW_ARRAY
- CALL

## 8.2 TypeEntry

StackMaps tell the GC where references are located.

But how does the GC know which fields inside an object contain references?

This is the responsibility of TypeEntry.

```python
@dataclass
class TypeEntry:
    type_id: int
    kind: int
    name: str
    field_count: int
    pointer_mask: int
```

The three object categories are:

```python
STRUCT = 1
ARRAY_OF_VALUES = 2
ARRAY_OF_REFERENCES = 3
```

### STRUCT

Represents an object containing fields.

Example:

```java
class Person {
    int age;
    Object address;
    int score;
}
```

Its memory layout:

```text
PERSON OBJECT

+-------------------+
| age = 25          | bit 0 = 0
+-------------------+
| address reference | bit 1 = 1
+-------------------+
| score = 100       | bit 2 = 0
+-------------------+

pointer_mask = 010 binary
```

The GC follows only the reference fields.

### ARRAY_OF_VALUES

Represents an array containing primitive values.

Example:

```java
int[] numbers = {10, 20, 30};
```

```text
+----+----+----+
| 10 | 20 | 30 |
+----+----+----+
```

The elements are not object references.

### ARRAY_OF_REFERENCES

Represents an array containing references to objects.

Example:

```java
Person[] people;
```

```text
+-----------+-----------+-----------+
| Person A  | Person B  | Person C  |
+-----------+-----------+-----------+
      |           |           |
      v           v           v
   Objects in the heap
```

The GC must follow these references.

## 8.3 How StackMap and TypeEntry work together

The process is:

```text
             GC ROOTS
                 |
                 v
           STACK MAPS
                 |
                 v
       Find reference locations
                 |
                 v
          HEAP OBJECTS
                 |
                 v
           TYPE ENTRY
                 |
                 v
       Inspect reference fields
                 |
                 v
        TRACE OBJECT GRAPH
                 |
                 v
        MARK REACHABLE OBJECTS
                 |
                 v
         RECLAIM THE REST
```

The StackMap identifies the references in active execution contexts.

The TypeEntry describes how to traverse the objects those references point to.

Together, they allow the GC to identify reachable objects without confusing integers with memory addresses.

| Code | Meaning |
|---|---|

## Benchmark observations

According to the project's benchmark documentation:

- Stop-and-Copy performs better when most allocated objects are garbage.
- Mark-and-Sweep performs better when the live set is large relative to a small heap.

There is no universally best algorithm. Performance depends on the workload and memory conditions.
